## Executive summary

Phase 0 — Truth & Integrity is the blocker phase of the WappFlow maturity roadmap: nothing in later phases ships until these nine findings are closed, because they are the points where the platform currently lies to itself or to a tenant. Each item was surfaced by the 2026-07-01 product audit, individually proposed, adversarially reviewed, and on 2026-07-01 re-confirmed LIVE against current code. The work is deliberately narrow and surgical — mostly route guards, body-parser ordering, one additive column, and two idempotent backfills — not a refactor. The Engineering Constitution priority order (Security > Data Integrity > Platform Consistency > Performance > Workflow > UX > Delight > Features) drives both the contents of the phase and the order in which the items land.

The headline is security. Two WhatsApp management routes (GET /api/whatsapp/status and POST /api/whatsapp/disconnect) have NO auth and act on global, workspace-agnostic state — /status even returns the pairing QR, so an unauthenticated caller can scan another tenant's QR and hijack their WhatsApp session. The Stripe webhook settles invoices with ZERO signature verification on a publicly whitelisted route, so anyone who can POST to it can mark arbitrary invoices paid. Lead sub-resource and reminder routes leak (and, the reviewer found, WRITE) cross-tenant by accepting an attacker-supplied lead_id with no preceding workspace guard. And the Command Center impersonation banner — the only visible 'you are impersonating / exit' control — is defined but mounted nowhere, so an admin can be silently acting as a customer.

The second axis is money and data integrity. There are two divergent 'paid' paths: the real payments ledger (settle → markPaid) and a frontend 'Mark as Paid' button that writes invoices.status='paid' directly, bypassing the ledger entirely — so the ledger is not the source of truth for revenue. Separately, ms_albums is declared TWICE with two different schemas (a full one in media-studio.js, a slim one with page_count in studio-ai.js), a latent dual-schema corruption that depends on mount order to stay benign.

The remaining items restore platform consistency and unblock workflows: plan/pricing/currency vocabulary still references dead tiers (free/starter/growth) in three frontend files that the live entitlements engine no longer knows about; phantom dead plan UI (PlanBanner, PlanChip, PlanWelcomeModal) keyed to those removed tiers should be deleted; and three user-facing workflows are simply broken — invoice email calls a nonexistent API method, ?tab=billing links render blank, and the Empty-Trash button throws. Together these nine items make the platform's own state — who you are, what you owe, what plan you're on, how many pages an album has — true again.

Several items gained important reviewer caveats that expand or correct their original scope and must carry into implementation: (1) wa-auth — the Security reviewer found the leak set was INCOMPLETE; PATCH /api/whatsapp/groups/:groupId accepts a caller-supplied account_id and drives the live WhatsApp session before any workspace check, so an account_id workspace-ownership guard must be added on top of the group guard. (2) ws-scope — the proposal FACTUALLY mis-stated that POST /api/leads/:leadId/notes (server.js:2062) and POST .../reminders (2086) were already guarded; they are NOT, and are live cross-tenant WRITE leaks that must join the fix set, plus the permanent-delete cascade (1953-1960) runs before the lead delete is workspace-scoped. (3) mark-as-paid — the Data-Migration reviewer found a backfill JOIN fan-out hole (a super_admin in >1 workspace would mint phantom revenue rows; absent in today's data but not prevented by schema) requiring a single-row correlated subquery and a COUNT>1 abort assertion. (4) ms-albums-schema — adding a real page_count column collides with an existing 'AS page_count' subquery (two same-named columns, last-wins ordering) and creates a stored-vs-live split-brain count that must be resolved. (5) stripe-webhook — the idempotency INSERT must use a generated id distinct from the Stripe event id, and webhook_events should only be written for handled event types. These caveats are reflected in the sequencing, migration plan, and risk register below.

## Consolidated migration plan

Consolidated, ordered, reversible migration view spanning the three items that touch data (ms-albums-schema, mark-as-paid, pricing-reconcile). All steps are additive (no column drops, no type changes, no renames), idempotent (CREATE ... IF NOT EXISTS / safeAlter swallows duplicate-column / WHERE ... IS NULL backfills), and each is independently revertible. Grandfathered studio_plus workspaces are respected throughout: pricing already normalized every legacy workspace_plan row to a valid tier on 2026-06-21, so NO migration step touches plan rows.

1. ms_albums canonical column (media-studio.js, runs at media-studio mount, before studio-ai mount): safeAlter('ALTER TABLE ms_albums ADD COLUMN page_count INTEGER'). REVERSIBLE: the column is nullable and unused by media-studio writes; leaving it is zero-cost, no rollback needed.
2. ms_albums self-healing defensive ALTERs (same block): idempotent safeAlter for cover_asset_id, pdf_status, pdf_storage_key, pdf_size, pdf_pages, pdf_built_at, created_by, updated_at — no-ops on the common media-studio-won DBs, heal the rare studio-ai-won DB so the canonical shape converges regardless of historical mount order.
3. ms_albums backfill (same block, guarded): UPDATE ms_albums SET page_count = (SELECT COUNT(*) FROM ms_album_pages p WHERE p.album_id = ms_albums.id) WHERE page_count IS NULL — touches only un-backfilled rows; matches zero rows after first boot. NOTE the unresolved semantics open question (stored 'actual pages' vs studio-ai 'intended pages'): if page_count is decided to mean intended pages, do NOT run this backfill from ms_album_pages — leave legacy rows NULL. Alias the colliding list query subquery to live_page_count so there are never two same-named columns. Then remove studio-ai's CREATE TABLE ms_albums and replace with a boot assertion that fails LOUDLY if the table is absent.
4. payments idempotency index (mark-as-paid) — CREATE BEFORE the backfill: CREATE UNIQUE INDEX IF NOT EXISTS uq_payments_invoice_paid ON payments(workspace_id, kind, ref_id) WHERE status='paid' AND kind='invoice'. Wrap in try/catch that logs and continues so a pre-existing legacy duplicate cannot crash boot (and is reported for manual cleanup). Creating it first protects the backfill INSERTs by constraint even if the NOT EXISTS guard is later edited.
5. payments migration marker (mark-as-paid): gate the backfill behind a one-row bookkeeping flag (the same pricing_config/migrations table pattern pricing.js uses) so it provably runs once and is auditable, in addition to the NOT EXISTS guard.
6. payments backfill for already-paid invoices (mark-as-paid): for every invoice with status='paid' lacking a paid payments row, INSERT a synthetic manual payment tagged provider='manual', provider_ref='backfill', description prefixed 'Backfilled:', status='paid', paid_at=invoices.created_at (coerce via datetime() if the legacy timestamp is loose). RESOLVE the workspace deterministically with a single-row correlated subquery — (SELECT wm.workspace_id FROM workspace_members wm WHERE wm.user_id=i.user_id AND wm.role='super_admin' ORDER BY wm.created_at ASC LIMIT 1) — or users.workspace_id as the authoritative owner→workspace link; NEVER a bare JOIN on user_id (fan-out = phantom revenue). Add a COUNT>1 abort assertion: if any invoice would map to more than one workspace, abort the backfill and report. REVERSIBLE: synthetic rows are tagged, so they can be deleted by provider_ref='backfill' if the backfill must be undone.
7. PUT /api/invoices/:id delegation (mark-as-paid): change the bypass route to detect status='paid' and route through the SAME idempotency-guarded markPaidByInvoice(invoiceId) helper as the new endpoint — never a blind INSERT — so old clients keep working with zero breakage. After markPaid, re-read invoice status and return a warning flag (and logAudit) if it is still not 'paid', surfacing settle() failures instead of masking them.
8. pricing vocabulary reconcile (pricing-reconcile): pure code change, NO data migration — workspaces already grandfathered to studio_plus and legacy tier rows already normalized on 2026-06-21. Make client PLAN_META[plan] access null-safe (fallback to DEFAULT label / nextPlanFor) so an unexpected server tier string never renders blank, and drive formatMoney's currency from the per-plan all_plans[].currency, treating 'PKR' strictly as the absent-value fallback.
9. ws-scope P1 (DEFERRED out of Phase 0 P0, listed for completeness): additive workspace_id columns + indexes on invoices/email_workflows, backfilled via the same super_admin mapping with a dual-read window ((workspace_id=? OR (workspace_id IS NULL AND user_id=?))) before switching to workspace_id-only, with unmatched-row counts reported. Keep entirely out of the P0 PR.

## Rollout sequence

Constraints: ONE production server (Hetzner), deployed manually by the maintainer (git pull + npm build + pm2 restart), no CI/CD, no staging, better-sqlite3 (synchronous, single-process). The goal is small, individually-verifiable, individually-revertible deploys. Group the nine items into four deployable batches, each its own commit/deploy with its own verification checklist, so a regression is bisectable to a single batch.

BATCH 1 — Security route guards (wa-auth, ws-scope P0, impersonation-banner). Code-only, no schema, no env. wa-auth and ws-scope must deploy backend+frontend together (atomic auth requirement on /status; auth-header edit in the same push). Per-deploy checklist: (a) curl /api/whatsapp/status WITHOUT a token → expect 401, WITH token → 200; (b) as workspace B, hit each :leadId sub-resource and the two POST write routes with a workspace-A lead id → expect 404; (c) confirm the legacy WhatsApp page still renders connected/disconnected (and not_initialized maps cleanly); (d) log in normally (non-impersonating) and confirm the impersonation banner is absent and zero visual change; (e) start an impersonation session and confirm the banner + Exit button appear. Rollback: git revert the commit + pm2 restart — no data to undo.

BATCH 2 — Stripe webhook (stripe-webhook). Deploy ALONE because of body-parser ordering risk and the env-var pairing. Rollout step ORDER: set STRIPE_WEBHOOK_SECRET first, then deploy. Feature-flag-by-config: behavior is naturally gated by whether Stripe is live (STRIPE_SECRET_KEY) on this deployment. Per-deploy checklist: (a) boot log asserts req.body is a Buffer for the webhook route; (b) boot warns if STRIPE_SECRET_KEY set but webhook secret unset; (c) Stripe CLI `stripe listen --forward-to` (or a recorded signed payload) yields a 200 and settles a test invoice; (d) an unsigned/forged POST is rejected 4xx; (e) a replayed event id is a no-op (duplicate). Rollback: revert the commit; manual Mark-as-Paid remains the human fallback in the gap, so payments never hard-stop.

BATCH 3 — Data-integrity migrations (mark-as-paid, ms-albums-schema). These carry backfills, so deploy together but as the most carefully watched push, ideally in a low-traffic window. Pre-deploy: snapshot/copy the sqlite DB file (cheap, single-file) as the rollback artifact. Migration order within the batch is fixed: ms_albums ALTERs+backfill (media-studio mount) → payments partial UNIQUE index → payments migration marker → payments backfill (with the COUNT>1 abort assertion) → PUT delegation. Per-deploy checklist: (a) boot logs show the backfill ran once (marker set) and report 0 unmatched/duplicate rows (else abort and investigate before opening traffic); (b) SELECT count of provider_ref='backfill' rows equals count of pre-ledger paid invoices; (c) mark an invoice paid via the button and confirm exactly one paid ledger row + invoice flips paid; (d) album list query returns a single deterministic page_count; (e) studio-ai boots without recreating ms_albums (assertion passes). Rollback: restore the DB file snapshot + revert code; synthetic rows are also deletable by provider_ref='backfill' if a partial undo is preferred.

BATCH 4 — Consistency + workflow (pricing-reconcile, then dead-code-purge, then broken-routes). Strict intra-batch order: reconcile rewires vocabulary → purge deletes the now-confirmed-dead UI → broken-routes wires the ?tab=billing→plan alias to the finalized tab id and the invoice-email/empty-trash repairs. All code-only, no schema. Per-deploy checklist: (a) next build passes; (b) smoke the 6 lock-consumer pages (settings, providers, knowledge, team, reports, leads-list) — tooltips/badges render, no 'Growth'/'Free' literals, no blank panes; (c) /settings?tab=billing resolves to the plan tab; (d) send a test invoice email end-to-end (SMTP configured) and confirm Print/Email render identically; (e) Empty-Trash runs inside a transaction, deletes only is_deleted=1 rows in the caller's workspace, and logs the count. Rollback: revert the commit + pm2 restart; deletions are recoverable from git history.

Across all batches: deploy one batch, run its checklist, watch logs for a beat, only then proceed to the next. Never combine batches in one deploy — the value of four small reversible pushes on a no-staging server is bisectability.

## Detailed work-item proposals

### `wa-auth` — Authenticate & workspace-scope the WhatsApp status/management endpoints
**Priority:** Security · **Effort:** S · **Affected:** backend/server.js (WhatsApp routes ~2571-2614 + new resolver helper; PATCH groups ~5119), backend/whatsapp-service.js (additive syncMissedForAccount(accountId) proxy on WhatsAppManager), wappflow-web/src/app/whatsapp/page.js (add Authorization header to fetchStatus; 401 handling)
**Depends on:** `Reuses existing auth middleware (server.js:158) — no change to it.`, `Reuses existing WhatsAppManager methods getStatus/disconnect/reconnect(accountId) (whatsapp-service.js:1028/1041/1052).`, `No dependency on other Phase 0 items; independent.`, `Frontend + backend must deploy together (atomic auth requirement on /status).`

**Problem.** The WhatsApp connection control plane is partially unauthenticated and the legacy paths are not workspace-scoped, in a multi-tenant SaaS where each workspace pairs its own WhatsApp number.

Enumeration of every /api/whatsapp* route (current backend/server.js):
1. GET /api/whatsapp/status (2571) — NO auth, NO scoping. Returns getLegacyStatus() including qrCode/phoneNumber. CRITICAL: cross-tenant session hijack (scan the QR) + phone-number/connection-state disclosure.
2. GET /api/whatsapp/accounts/:id/status (2574) — auth + scoped. OK.
3. POST /api/whatsapp/accounts/:id/connect (2581) — auth + scoped. OK.
4. POST /api/whatsapp/accounts/:id/disconnect (2588) — auth + scoped. OK.
5. POST /api/whatsapp/disconnect (2595) — NO auth, NO scoping. Disconnects the legacy session. CRITICAL: unauthenticated DoS.
6. POST /api/whatsapp/reconnect (2600) — auth present, but NOT workspace-scoped: calls whatsappService.reconnect() with no accountId -> operates on __legacy__. Any authed user in any workspace can drive the shared legacy session. SECONDARY.
7. POST /api/whatsapp/sync-missed (2608) — auth present, NOT scoped: syncMissedMessages() iterates ALL instances across ALL workspaces. SECONDARY.
8. POST /api/whatsapp/send (2616) — auth present. MESSAGE FLOW — explicitly out of scope (HARD CONSTRAINT). Untouched.
9. GET /api/whatsapp/ready-accounts (5027) — auth + filters to req.workspaceId. OK.
10. POST /api/whatsapp/groups (5045) — auth + scopes leads by workspace. OK.
11. PATCH /api/whatsapp/groups/:groupId (5119) — auth present, but the group ops call the service before verifying the groupId belongs to a whatsapp_groups row in req.workspaceId. MINOR scoping gap.

Net: 2 critical (unauth), 2 secondary (authed but legacy/global), 1 minor.

**Root cause.** These two routes predate the multi-account refactor. When per-account routes (/accounts/:id/*) and the WhatsAppManager (instances Map keyed by accountId, with __legacy__ fallback) were added, the original single-tenant /status and /disconnect handlers were left in place for backward compatibility with the legacy WhatsApp page (wappflow-web/src/app/whatsapp/page.js) and never had the auth middleware or workspace resolution retrofitted. getLegacyStatus()/disconnect() with no accountId resolve to a single global session, which was acceptable when WappFlow was single-tenant but is now a tenant-isolation hole. reconnect/sync-missed got auth bolted on but kept their no-arg (global) service calls, so they are authenticated but not scoped.

**Proposed solution.** Additive, no rewrite, no second implementation. Reuse the EXISTING auth middleware (server.js:158) and the EXISTING per-account scoping query already used by routes 2574/2581/2588. Introduce ONE small shared resolver helper and apply it to the legacy routes so they become authed + scoped while preserving their response shape.

1) Add a helper near the WhatsApp routes (server.js, just before line 2571):
function resolveWorkspaceWaAccount(workspaceId) {
  return db.prepare("SELECT * FROM platform_accounts WHERE workspace_id = ? AND platform = 'whatsapp' ORDER BY slot_index ASC LIMIT 1").get(workspaceId);
}

2) Route 1 — GET /api/whatsapp/status: add auth; resolve the workspace account; return that account's status (or a disconnected stub if none), NOT getLegacyStatus():
app.get('/api/whatsapp/status', auth, (req, res) => {
  const account = resolveWorkspaceWaAccount(req.workspaceId);
  if (!account) return res.json({ status: 'disconnected', isReady: false });
  res.json(whatsappService.getStatus(account.id));
});
This removes cross-tenant QR exposure: getStatus(accountId) returns only the calling workspace's session.

3) Route 5 — POST /api/whatsapp/disconnect: add auth; resolve account; pass the accountId so the manager disconnects THIS workspace's instance, not __legacy__:
app.post('/api/whatsapp/disconnect', auth, async (req, res) => {
  const account = resolveWorkspaceWaAccount(req.workspaceId);
  if (!account) return res.status(404).json({ error: 'No WhatsApp account for this workspace' });
  try { await whatsappService.disconnect(account.id); res.json({ message: 'Disconnected' }); }
  catch (e) { res.status(500).json({ error: 'Failed to disconnect' }); }
});

4) Route 6 — POST /api/whatsapp/reconnect: keep auth; resolve account; pass accountId: await whatsappService.reconnect(account.id) (response-immediately pattern preserved). If no account, 404.

5) Route 7 — POST /api/whatsapp/sync-missed: keep auth; resolve account; call a scoped sync. Add a thin manager method syncMissedForAccount(accountId) (additive proxy mirroring the existing reconnect(accountId)/disconnect(accountId) proxies in whatsapp-service.js) instead of the global syncMissedMessages(). If no account/not ready -> 400/404 as today.

6) Route 11 — PATCH /api/whatsapp/groups/:groupId (MINOR, include here): before calling the service, verify ownership: SELECT 1 FROM whatsapp_groups WHERE workspace_id=? AND group_id=?; 404 if absent. No service signature change.

7) Frontend (wappflow-web/src/app/whatsapp/page.js): fetchStatus() at line 28 must send the bearer token (mirror the existing pattern at line 41/53): fetch(.../status, { headers: { Authorization: 'Bearer ' + localStorage.getItem('token') }, cache: 'no-store' }). The disconnect call already sends the token. Handle 401 by redirecting to /login (the page already guards on localStorage user).

No changes to message send/receive logic (route 8 and whatsapp-service.js send/receive paths untouched).

**Golden-Rule check (reuse/unify).** No second implementation introduced. Reuses: (a) the existing auth middleware (server.js:158) verbatim — same req.workspaceId/req.userId it already sets; (b) the exact scoping predicate already used by the per-account routes (platform_accounts WHERE workspace_id=? AND platform='whatsapp', server.js:2575/2582/2589) — factored into one resolveWorkspaceWaAccount helper instead of being copy-pasted; (c) the existing manager methods whatsappService.getStatus(accountId) / disconnect(accountId) / reconnect(accountId) (whatsapp-service.js:1028/1052/1041), which already accept an accountId — we simply stop passing nothing. The only new code is the resolver helper and one additive syncMissedForAccount(accountId) proxy that mirrors the existing per-account proxies. The legacy getLegacyStatus() / no-arg disconnect() paths are retained for any remaining internal callers (Refactor/Extend, not Delete) — grep in rollout and delete getLegacyStatus if unreferenced after this change.

### `stripe-webhook` — Verify Stripe webhook signatures + add payment idempotency
**Priority:** Security · **Effort:** S · **Affected:** backend/payments.js (webhook handler + signature/idempotency guards), backend/server.js (path-scoped express.raw registration before global express.json at line 80; reuses webhook_events table at line 713), backend/.env.example (document STRIPE_WEBHOOK_SECRET)
**Depends on:** `No new npm packages (uses existing crypto + express ^5 express.raw).`, `Requires STRIPE_WEBHOOK_SECRET env var and a configured Stripe Dashboard webhook endpoint on Stripe-enabled deployments (ops step, not a code dependency).`, `Reuses existing webhook_events table (server.js:713) and existing markPaid/settle path (payments.js:63-74) — no other Phase 0 item blocks this.`

**Problem.** The Stripe webhook endpoint `POST /api/payments/webhook` (backend/payments.js:117-128) accepts any unauthenticated POST and marks the referenced payment — and its linked invoice or print order — as PAID without verifying the request actually came from Stripe. The route is publicly exempted from auth and the module gate (server.js:5441). An attacker who knows or guesses a payment id (or harvests one via the public pay page) can forge a `checkout.session.completed` body and obtain free fulfillment across any workspace. Separately, there is no idempotency: duplicate or replayed Stripe deliveries (Stripe retries on any non-2xx and can deliver the same event more than once) can re-settle a payment, re-emit the `payment_paid` SSE broadcast, and append duplicate contact-history rows. Both are violations of the constitution's top priorities (Security, then Data Integrity).

**Root cause.** The webhook was shipped as an intentional stub: payments.js:114-116 carries a TODO admitting signature verification was deferred "when enabling Stripe." Two structural facts compounded it: (1) the backend mounts a global `express.json()` body parser at server.js:80 ahead of all routes, so the raw request bytes required for an HMAC signature check are already consumed and gone by the time the webhook handler runs — verification was non-trivial to bolt on after the fact; (2) the project deliberately avoids the Stripe SDK (raw fetch only), so the usual `stripe.webhooks.constructEvent` helper was not available and a hand-rolled HMAC verifier was never written. Idempotency was never added because the happy-path `p.status !== 'paid'` check looked sufficient in isolation, and the pre-existing `webhook_events` dedup table (server.js:713) was never actually wired up for any provider.

**Proposed solution.** Harden the existing webhook in place; do not add a second handler. Three additive changes, all inside backend/payments.js plus one raw-body parser registration in server.js, gated on env so manual-only deployments are unaffected.

1) RAW BODY (scoped, before global JSON). In server.js, immediately BEFORE line 80 (`app.use(express.json(...))`), register a raw parser bound only to the webhook path:
   `app.use('/api/payments/webhook', express.raw({ type: 'application/json', limit: '1mb' }));`
   Express matches the first body-parser that fits the path; because this is registered first and is path-scoped, the global JSON parser at :80 will skip the already-parsed webhook request (req.body becomes a Buffer for that route only, JSON for everything else). No other route changes. This is the standard Stripe pattern adapted to the no-SDK constraint.

2) SIGNATURE VERIFICATION (manual HMAC, no SDK) inside the existing handler in payments.js. Read `STRIPE_WEBHOOK_SECRET` (new env, alongside the existing STRIPE_SECRET_KEY read at payments.js:24). Behaviour:
   - If `STRIPE_WEBHOOK_SECRET` is unset → the deployment is manual-only or pre-launch. Reject every webhook POST with 400 `{error:'webhook not configured'}` (closes the forgery hole even before Stripe is enabled; settlement still works via the authed mark-paid route).
   - If set → parse the `Stripe-Signature` header (`t=<ts>,v1=<sig>` pairs), recompute `crypto.createHmac('sha256', secret).update(`${t}.${rawBuf}`).digest('hex')`, compare to v1 using `crypto.timingSafeEqual`, and reject if mismatch (400) or if the timestamp is older than a 5-minute tolerance (replay window). Only after a valid signature, `JSON.parse(rawBuf)` to get the event. `crypto` is already required at payments.js:13.

3) IDEMPOTENCY by Stripe event id, reusing the dead `webhook_events` table (server.js:713-719, `UNIQUE(platform,event_id)`). After signature passes, attempt `INSERT INTO webhook_events (id, platform, event_id) VALUES (?, 'stripe', ?)` with the Stripe `ev.id`. If the insert throws a UNIQUE violation, the event was already processed → return 200 `{received:true, duplicate:true}` and do nothing (Stripe stops retrying on 2xx). Only on a fresh insert do we proceed to settle. This makes processing exactly-once per event id. Keep the existing `p.status !== 'paid'` guard (payments.js:124) as defence-in-depth. Also add the same `status !== 'paid'` short-circuit semantics are already present; markPaid's UPDATE is naturally idempotent on the row.

Always return 2xx for accepted-or-duplicate so Stripe stops retrying; return 4xx ONLY for signature/parse failures (so Stripe surfaces misconfiguration). Wrap settlement so a downstream error still returns 200 to avoid infinite Stripe retries on a poison event — mirrors the current best-effort catch at payments.js:127.

The WhatsApp send/receive flow is untouched. No message logic changes. Only the payments webhook route and one path-scoped parser are added.

### `mark-as-paid` — Route Mark-as-Paid through the single payments ledger

**Root cause.** The invoice-status field and the payments ledger were built as independent features. invoices.status is a free-form column updated by a generic PUT /api/invoices/:id (server.js:2229) that accepts any status including 'paid'. **Proposed solution.** Make the payments ledger the ONLY way an invoice becomes 'paid'. Three additive changes, no rewrites:

One ledger row per paid transition, guaranteed. This is pure reuse of markPaid/settle (Golden Rule).

2) CLOSE the bypass. In PUT /api/invoices/:id (server.js:2229), stop honoring status='paid' coming from the generic update. If the incoming status==='paid' and the invoice is not already paid, return 409 {error:'Use the payments endpoint to mark an invoice paid', use:'/api/payments/invoice/:id/mark-paid'} OR (preferred for backward-compat) internally delegate to the same shared markPaid-by-invoice logic so old clients still work.
